# Telemetry Schema and Attribute Contract

Observability is easier to operate when logs, metrics, and traces use a small set of stable identities and naming rules. Treat those fields as a contract: dashboards, alerts, searches, retention rules, and incident runbooks may depend on them even when the application itself does not.

This guide is backend-neutral. OpenTelemetry semantic conventions are used where they provide an established name, but the same contract principles apply if telemetry is routed to CloudWatch, OpenSearch, or another platform.

## Minimum Resource Identity

Set a stable identity before telemetry leaves the workload. At minimum, define:

| Attribute | Purpose | Guidance |
| --- | --- | --- |
| `service.name` | Identifies the logical service | Set explicitly; do not rely on an `unknown_service` fallback. |
| `service.namespace` | Groups related services | Use when service names could collide across products or platforms. |
| `service.version` | Identifies the deployed release | Prefer an immutable release, image, or build version when available. |
| `deployment.environment.name` | Separates development, staging, production, and similar tiers | Use a controlled vocabulary and keep it consistent across logs, metrics, and traces. |

OpenTelemetry documents `service.name` as the logical service identity and recommends setting it explicitly. It also defines `deployment.environment.name` for deployment-tier identification. See the [OpenTelemetry resource guidance](https://opentelemetry.io/docs/concepts/resources/) and [service semantic conventions](https://opentelemetry.io/docs/specs/semconv/resource/service/).

Do not overload resource identity with request-specific values. User IDs, order IDs, trace IDs, URLs containing identifiers, or arbitrary container/task IDs should not become global resource attributes.

## Log Contract

For structured application logs, prefer fields with stable meaning rather than free-form parsing rules.

Recommended contract:

- timestamp generated by the application or logging library;
- severity or level with a controlled set of values;
- concise message or event name;
- stable service and environment identity;
- trace and span identifiers when correlation is available;
- error type and a sanitized error description when an operation fails.

Avoid putting credentials, tokens, personal data, raw request bodies, or unbounded payloads into the contract. Follow [sensitive telemetry handling](sensitive-telemetry-handling.md) for redaction and prohibited-field guidance.

Field names used by dashboards or alerts should not be renamed casually. If a field must change, use the compatibility process below.

## Metric Contract

Metrics should remain aggregatable and inexpensive to query.

- Give each metric a stable name and unit.
- Keep dimensions low-cardinality and operationally meaningful.
- Prefer controlled values such as service, environment, operation, or status class.
- Do not use request IDs, user IDs, full URLs, timestamps, UUIDs, or other near-unique values as metric dimensions.
- Do not encode environment or version into the metric name when a stable resource attribute can represent it.
- Document whether a metric is a counter, gauge, histogram, or other instrument and what decision it supports.

Review new dimensions against the [cost and cardinality guardrails](cost-and-cardinality-guardrails.md) before rollout.

## Trace Contract

Span names and attributes should support comparison across many requests rather than reproduce raw request data.

- Use stable operation names; do not place customer or object identifiers in span names.
- Preserve service and environment resource identity across the trace path.
- Use standard semantic attributes where an OpenTelemetry convention already exists.
- Add custom attributes only when they support a defined troubleshooting or service-level question.
- Keep high-cardinality attributes out of metrics derived from traces unless the aggregation path explicitly controls them.
- Do not capture sensitive request or response payloads merely because tracing supports arbitrary attributes.

OpenTelemetry semantic conventions provide common naming across signals; see the [semantic conventions overview](https://opentelemetry.io/docs/concepts/semantic-conventions/).

## Compatibility Rules

Treat changes to telemetry used by alerts, dashboards, searches, SLOs, or runbooks as interface changes.

1. **Prefer additive changes.** Add a new field before removing or renaming an existing one.
2. **Update consumers first.** Make dashboards, alerts, parsers, and queries understand the new field before producers stop emitting the old field.
3. **Use a transition window.** Where practical, emit both old and new fields long enough to validate the migration.
4. **Measure coverage.** Confirm the new field is present for representative services, environments, and failure paths.
5. **Remove deliberately.** Remove the old field only after dependent consumers have migrated and the rollback path is understood.
6. **Record the change.** Note the owner, date, affected signals, consumers, and validation evidence.

A schema change that makes an alert silently stop matching is an observability regression even when the application deployment itself succeeds.

## Contract Register Template

Use a lightweight register for telemetry that has operational consumers.

| Signal | Field or metric | Meaning | Allowed values / unit | Cardinality expectation | Consumers | Owner | Change notes |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Resource | `service.name` | Logical service identity | Controlled service name | Low | All dashboards and traces | Service team | Stable |
| Resource | `deployment.environment.name` | Deployment tier | `development`, `staging`, `production` or approved equivalent | Low | Dashboards, alerts, indexes | Platform | Stable |
| Metric | `http.server.request.duration` or adopted equivalent | Request latency | Time unit documented by implementation | Low dimensions | Latency dashboard, SLO | Service team | Review semantic-convention version before adoption |
| Log | `event.name` or adopted equivalent | Machine-queryable event category | Controlled vocabulary | Bounded | Searches, alerts | Service team | Additive changes preferred |

The exact fields depend on the instrumentation library and semantic-convention version. Record the convention or internal schema version when a consumer relies on a specific name.

## Review Checklist

Before adding or changing telemetry, confirm that:

- [ ] service and environment identity remain stable across all three signals;
- [ ] new metric dimensions have a bounded value set;
- [ ] span and log fields do not expose sensitive or request-specific data unnecessarily;
- [ ] dashboards, alerts, searches, and SLOs affected by a rename have a migration plan;
- [ ] the change is tested with representative success and failure traffic;
- [ ] the contract owner and rollback path are known;
- [ ] semantic-convention names are checked against the version actually used by the instrumentation stack.

The goal is not to freeze telemetry forever. The goal is to make changes explicit enough that observability remains trustworthy while the system evolves.
